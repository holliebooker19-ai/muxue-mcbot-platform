# 通用工作站设计

2026-10-07 起草。起因：8d 的 `craft-item`、`smelt-item` 写死了原版工作台和三种炉子，附魔台、铁砧、酿造台等都不支持，模组工作台也没有接入办法。设计参考了一份外部评审（GPT），下面写的是采纳后的方案：哪些照做、哪些简化或推迟，以及为以后支持 Fabric 和更新的 1.21.x 预留的接口。

## 目标

- 原版工作站全部由同一套核心执行：合成（背包 2×2、工作台）、熔炉类三种、切石机、酿造台、锻造台、砂轮、织布机、制图台、附魔台、铁砧。
- 模组工作台好接：“几个原料格＋燃料格＋成品格＋一种配方”这类常见机器，几十行 Java 或一份 JSON 就能接上；特殊的再写小段 Java。
- 交给模型的工具少而明确，不让模型点格子、猜按钮号。
- 核心代码不依赖加载器，以后加 Fabric、更新的 1.21.x 时只换薄薄一层。

## 原则（沿用现有的，评审补充的几条加了说明）

1. **默认只走玩家原生入口**：开界面、点击、按按钮、右键，都走 `handleContainerClick`、`handleContainerButtonClick`、`handleUseItemOn`、`handleRenameItem` 这些玩家数据包入口。原版和模组挂在这些路径上的副作用（经验、进度、统计、配方解锁、保护插件的事件）照常发生。不说“兼容所有保护插件”，只说“走了玩家路径上已有的检查”，具体保护模组要实测。
2. **8b 的物品能力存取是另一种模式，不是后备**：NeoForge 的 `Capabilities.ItemHandler.BLOCK`（Fabric 是 Transfer API 的 `ItemStorage.SIDED`）是给漏斗、管道用的自动化接口，没有玩家身份。它要标成 `AUTOMATION` 模式，服主按适配器、按方向面显式开启；回执写明“自动化存取，不保证玩家副作用”。界面路径失败时**不**自动改走能力路径。
3. **材料分三类**：
   - 普通材料（`PLAIN_MATERIAL`）：现有规则，没有任何附加组件的栈，用于配料、燃料。
   - 配方声明的组件材料（`RECIPE_COMPONENT`）：比如酿造用的水瓶、粗制药水，只放行配方要求的那种组件，按实际组件比较。
   - 指定的加工对象（`EXPLICIT_SUBJECT`）：铁砧、附魔、砂轮、锻造台要加工的装备。必须由模型先查到、拿到服务端给的引用（`subjectRef`，绑定栈的位置和完整内容），执行前逐字段比较，变了就作废。不设全局的“允许特殊物品”开关。
4. **回执以实际观察为准**，区分：交给工作站的（`delivered`）、确认消耗的（`consumed`）、确认产出的（`produced`）、进了背包的（`collected`）、返还的（`returned`）、还留在工作站里的（`remainingAtStation`）、原地变化的（`transformed`，比如水瓶变药水、装备被附魔）、经验变化。看不到的就不填，不拿配方预测来填。物品比较带组件，只按物品 id 数数会漏掉药水和装备的变化。
5. **失败分清楚**：没动手就被拒 → `failed`；做了一部分、剩下做不了 → `failed` 并报告做了的部分；在等热源、等加工 → `running` 并报告卡在哪；可能动过但核对不了 → `unknown`，只允许观察，不自动重试。
6. **花经验、可能毁装备的操作要有上限**：附魔、铁砧、砂轮先查后做；执行时带 `maxLevels`（最多扣几级）等上限，界面上的实际花费或结果和查询时不同就停下。附魔只按界面公开显示的提示授权，不用服务端权限偷看隐藏的附魔。超出上限的确认要来自玩家（游戏里说话）或服主，模型自己传 `confirmed:true` 不算。
7. 不计算、不校验哈希；比较用实际字段。

## 分层

| 层 | 内容 | 公开？ |
| --- | --- | --- |
| 工作站适配 `WorkstationAdapter` | 认方块、认界面、给出端口布局、配方来源、燃料和进度读法、用哪种执行模板 | 公开（`api.workstation`） |
| 端口布局 `StationLayout` | 逻辑端口 → 界面格：原料、加工对象、催化剂、燃料、盛器、成品、返还物、只读缓冲 | 公开 |
| 配方来源 `RecipeSource` | 按想要的产物或手上的原料查配方；三种实现：RecipeManager、计算型（酿造、铁砧）、界面选项型（附魔、切石） | 公开 |
| 执行模板 | 网格合成、加工机器（放料→等→取）、按钮选项、原地加工（酿造）、改造（铁砧、附魔、砂轮、锻造） | 内部实现，适配器只选用 |
| 材料求解 | 普通栈筛选、组件材料、加工对象核对、全局分配、缺料报告 | 内部 |
| 原生动作 | 寻路、开界面、点击、按钮、改名、关界面 | 内部 |
| 操作和回执 | 写权、状态、证据、错误码 | 内部 |
| 加载器服务 `LoaderPlatform` | 模组版本、燃烧时间、（8b）物品能力、事件桥 | 内部接口，每个加载器一份实现 |

和现有接口的关系：`ContainerAdapter` 继续只管“这个界面的哪些格属于这个容器”，`ItemInteraction` 继续只管一次右键。`WorkstationAdapter` 是新的第三种登记，可以引用它们（比如砧板复用右键交互）。登记和分派都还走 `McbotApi` 和 `ModAdapters`，id 共用一个命名空间，重复的拒绝。

### 逻辑端口

| 端口 | 含义 | 例子 |
| --- | --- | --- |
| `INGREDIENT` | 普通配料，会被消耗 | 合成网格、熔炉原料格、厨锅 6 格 |
| `SUBJECT` | 被加工的对象，结果可能就在原格 | 酿造台 3 个瓶位、铁砧左格、附魔台物品格 |
| `CATALYST` | 第二输入或催化剂 | 铁砧右格、附魔台青金石、锻造台模板 |
| `FUEL` | 工作站自己的燃料 | 熔炉燃料格、酿造台烈焰粉 |
| `CONTAINER` | 盛装用品 | 厨锅的碗格 |
| `RESULT` | 可以取走的成品 | 合成结果格、熔炉成品格、厨锅出餐格 |
| `BUFFER` | 机器内部的中间产物，只看不拿 | 厨锅里做好还没盛出来的菜 |

端口只能对应已核对过的位置。界面格号、方块存储格号、能力格号是三套编号，适配器要说清用的是哪种；第一阶段只有界面格。

### 执行模板

| 模板 | 工作站 | 提交点 |
| --- | --- | --- |
| `GRID_CRAFTER` | 背包 2×2、工作台、模组工作台 | 从成品格取走时 |
| `PROCESSOR` | 熔炉、烟熏炉、高炉、模组炉、厨锅 | 料齐后机器自己开始；可以等到取完，也可以放完就返回、以后来取。目前按单原料执行：多原料机器要等具体适配，布局不支持的会拒绝 |
| `OPTION_PICKER` | 切石机、织布机、制图台 | 选按钮后从成品格取走时 |
| `IN_PLACE` | 酿造台 | 料齐后机器自己开始，结果在原格 |
| `MODIFIER` | 锻造台、砂轮、铁砧、附魔台 | 附魔：按选项按钮那一下；铁砧／砂轮／锻造台：取成品时（铁砧改名只是配置） |

评审建议让第三方适配器自己返回一串受限步骤（放料、选项、等待、取出）。这次先只做内置模板：现有的需求（原版全部、Iron Furnaces、农夫乐事厨锅和砧板）都能套进上面五种。等真有套不进去的模组再加“自定义步骤”这个口子，接口里先留位置。

## 给模型的工具

保留 `craft-item`、`smelt-item`，参数和行为不变，内部改用新核心。再按任务意图加三个：

| 工具 | 用途 | 阶段 |
| --- | --- | --- |
| `workstation-options` | 查附近有哪些工作站、某个东西怎么做、有哪些选项（切石机结果、附魔三个选项和花费、铁砧结果和花费）、缺什么；返回之后执行要用的引用 | B |
| `produce-item` | 按目标产物做：切石、酿造、模组机器、厨锅；数量要写单位（要几个产物，还是做几次） | B |
| `modify-item` | 加工指定的装备或物品：附魔、铁砧、砂轮、锻造、织布、制图；必须带 `subjectRef` 和花费上限 | C |

取成品沿用 `smelt-item` 不带 input 的方式（打算以后并到 `produce-item` 的 `collect`，还没做），不另开工具。查询、等待、停止都用已有的操作工具。第三方接新机器不加新工具。模型不能传格号、按钮号或执行模式。

评审里的 `requestId` 幂等和 `productionRef` 先不做：运行端从不自动重放 `unknown` 的操作，回来取东西按工作站位置定位就够了；等以后断线重连真要重放请求时再加。

## 配方和缺料

- 配方来源三种：`RecipeManager` 型（合成、烧炼、切石、锻造、模组注册的配方）、计算型（酿造读 `level.potionBrewing()`，铁砧按原版规则算）、界面选项型（附魔台的三个选项、切石机的结果列表，从打开的界面读）。
- 材料匹配一律用服务端的判断（`Ingredient.test` 或模组自己的匹配），列出来的可选物品只用来解释。
- 分配要全局考虑：一格接受任意木板、另一格只要橡木板时，不能先把橡木板用光。先排约束最强的格，必要时回溯；网格很小，确定性求解就够。每格还要能叠成一叠（不同组件不能混）。
- 缺料报告来自同一次分配：每个需求写清可选物品、需要、已分到、还差，以及被排除的原因（被保护、带组件）。热源、青金石、经验等级、背包空间不够这类写进 `blockers`，不冒充“缺物品”。
- 放好料后以工作站实际显示的结果为准（现有的 `RECIPE_REFUSED`）；自动机器按自己的规则挑配方，对不上就停。

## 加载器和版本（为 Fabric 和更新的 1.21.x 预留）

交付计划里已经定了以后要支持更新的 1.21.x NeoForge 和 Fabric。这次的约束：

1. **核心不碰加载器**：除了下面登记的“加载器文件”，模组源码里不准出现 `net.neoforged`。构建时有检查（`loaderNeutralCheck`），违反就失败。目前 ServerBody 的绝大部分本来就只用原版类，加载器相关的集中在：入口和事件注册（`McbotServerControl`）、事件处理参数（`ServerController`、`SurvivalActions`、`ValidationProtection`、`RespawnValidationFixture`）。Iron Furnaces 的适配（`IronFurnaceAdapter`）原先也在核心里，现已移到独立附属模组 `mcbot-iron-furnaces`，不再受这条检查约束。
2. **加载器服务 `LoaderPlatform`**：模组版本（NeoForge 的 `ModList`／Fabric 的 `FabricLoader`）、燃烧时间（NeoForge 的 `getBurnTime`／Fabric 的 `FuelRegistry`）、以后 8b 的物品能力（NeoForge `IItemHandler`／Fabric `Storage<ItemVariant>`，后者自带事务）。核心只调这个接口。
3. **标签用 `c:` 命名空间**：`c:ores`、`c:stones` 在 NeoForge 和 Fabric 上是同一个标签，代码里直接用 `TagKey.create`，不用 NeoForge 的 `Tags` 类。
4. **映射**：NeoForge 用 Mojang 官方名＋Parchment；Fabric Loom 也可以用 `officialMojangMappings()`，所以同一份核心源码两边都能编译。
5. **以后的工程结构**：真正开始做 Fabric 时，拆成 `common`（核心＋公开 API）、`neoforge`、`fabric` 三个子项目（MultiLoader 模板的做法，不引入 Architectury 运行时依赖）。事件桥（tick、聊天、拾取、受伤、交互）要在两边各写一份：Fabric API 没有的事件（比如拾取前、即将受伤）要用 Mixin。现在不拆，只守住第 1 条，拆的时候就是搬文件。
6. **游戏版本比加载器更难**：1.21.2 起配方和燃料的接口都改了（配方展示、`FuelValues`、`RecipeInput`），所以配方读取放在 `RecipeSource` 后面，换版本时只重写这几个实现。不追求一份代码同时编译多个游戏版本。
7. **公开 API 只用原版类型和 JDK 类型**：附属模组的适配逻辑因此能在两个加载器之间复用大部分；但被适配的模组在两个加载器上往往是不同的代码（比如农夫乐事的 Fabric 移植版类名不同），适配器本身仍按“模组＋加载器＋版本”锁定。`McbotApi.versionsMatch` 改为核对当前加载器自己的版本。

## 迁移时要防的坑

- 每次点击都重新读当前界面的状态号、格子和光标，不预先生成一串点击；状态号只是同步版本，不是锁。
- 按钮包没有状态号，按之前要再核对一次当前选项。
- 放进一件东西后，结果、花费、按钮列表都可能马上变；自动开始加工的机器，最后一次放料就是提交点。
- 关界面不会回滚；机器里放进去的东西会留下，回执要写清楚。
- 平台锁只能锁住自己的 Bot，锁不住玩家、漏斗和其他模组；工作站里原有的东西默认是别人的，不清空。
- 重开界面就是新会话，旧的格号和选项引用作废。
- 多方块结构要分清交互位置、控制方块、存储位置。
- 区块卸载时不留着失效的方块实体；看不见时是 `running`（被挡住），重新加载后核对不上才是 `unknown`。
- Iron Furnaces 现在只认“没点燃、普通炉子模式”。迁到 `PROCESSOR` 时，点燃中是正常状态，不能被自己拒绝；工厂、发电机、升级界面继续拒绝。

## 进度

- **A（10-07 完成）**：见交付计划 8l。
- **B、C（10-07 完成）**，实现时的取舍：
  - 模板加了 `OPTION_PICKER`、`IN_PLACE`、`MODIFIER`；适配接口加了 `options`（按钮选项）、`levelCost`、`fuelLeft`（10-09 又加了可选的 `progress`，不开界面读进度，见 8b），配方来源加了 `isIngredient`、`transform`（原地变化，酿造用）。原版切石机、酿造台、附魔台、铁砧（三种破损程度）、砂轮、锻造台、织布机、制图台都是内置适配。
  - 工具按设计是 `workstation-options`、`produce-item`、`modify-item`。预览不另开工具：`modify-item` 带 `preview:true` 就是预览，走过去、放进去、读结果和花费、全部拿回。
  - 物品引用（ref）是随机串，绑定那一格和那一叠的完整内容；预览或被拒绝后东西拿回来可能换了格子，ref 跟着指到拿回后的那一格（内容必须完全一样），提交后作废。
  - 花经验的确认：工具说明和启动 prompt 要求模型先预览、告诉玩家花多少级、玩家同意后再做，服务端只按 `maxLevels` 卡上限、按 `expect` 卡结果。设计里说的“来自玩家或服主的可信确认”还没做，现在模型自己传的 maxLevels 就是放行条件。也就是说，“先预览、问过玩家再做”目前只是提示词约定，程序不验证玩家是否真的同意。
  - 酿造的规划：从背包里的瓶子出发，用背包里的材料，广度优先找最多 4 段；找不到时改用所有能当酿造材料的物品再找一次，只用来说明缺什么。烈焰粉可能被当成材料用掉（例如力量药水），燃料不足时报 NO_FUEL。
  - 回执的物品计数改成带组件的写法（`ItemDescriptions.key`），craft-item、smelt-item 的回执还是旧写法没动。“交付／消耗／产出”三者分开的字段没做，现在用 `inventoryChange` 加各自的 `made`、`stagesDone`、`leftInStation`。
  - 实测时发现：酿造要站着等 40 秒，期间运行端的后台观察读到“非储物界面”就报错，整个控制权被结束。改成 Bot 自己正在用的、适配器认得的工作站界面可以只读观察，`click-slot` 仍然不能点它。
  - 材料分配换成全局求解（约束最强的格先选，选不下去就回退）。
