## 1. 已确认的需求

2026-10-03 外部评审继续支持 ServerBody 路线，近期先修异步切换归属、原生写后未知结果和 Claude 宿主权限三处边界。实现、离线证据与未关闭项见[边界修复记录](archive/boundary_review_fixes.md)；混合故障回归优先于新增持续玩法。

随后[混合故障回归](archive/server_mixed_validation.md)已完成，补齐R4容器任务的共享锁与停止确认；包含约5分钟真实程序连续运行及Claude-b实际10阶段。R5/R6由下一批不同Mod样本推动，当前依然不外推为任意Mod或长期稳定。

1. Agent 框架默认在用户本机运行，尤其保留现有 Claude Code 运行／登录环境；用户也可以主动选择另一台 Agent 机器。
2. 本机不要有大量额外负载，不能把“再开一套大型整合包客户端”作为普通用户的默认前提。
3. 用户接受 Mod 服安装 MCBOT 服务端组件；单机应复用已有的内置服务器。
   用户进一步明确：服务端承担 Bot 的正常模拟开销是合理成本，不纳入本轮方案取舍或验收预算；不再把服务端资源对照作为开工前置关口。本机约束是避免额外完整 MC 客户端和不必要的 Agent 侧负载。
4. 目标仍面向其他用户、不同 Mod／服务器和多 MC 版本。新前提改变部署条件，不把产品退回仅支持某一台自有服。
5. Claude、Codex、DeepSeek Harness、Antigravity 与原生 API 通道仍是独立接入目标；优先可玩原型，但先验证关键假设。

本地 Agent 指 CLI／工具循环、MCP、记忆和凭据所在机器，不等于要求模型权重在本机推理。使用远端模型服务与把 Agent 进程搬到异地是两回事。服务端身体不应持有 Agent 登录凭据或模型 API Key，也不负责启动模型进程。

Claude Code 官方说明存在会话始终留在本机的部署方式，MCP／本机环境随本机会话保留；这支持“Agent 所在地与操控界面可以分离”，**不作为任何账号风控保证**。具体风控触发条件未核实，也不据此推荐迁移账号环境。[官方 Remote Control 说明](https://code.claude.com/docs/en/remote-control)

## 2. 部署必须独立配置

```text
Agent 主机（默认用户电脑，也可由用户选择独立机器）
  Claude Code / 其他 Agent / 原生 API 循环
          ↕ 本机工具调用
  MCBOT 工具、记忆、事件、控制桥
          ↕ 经鉴权的游戏控制通道
游戏主机（单机已有内置服务器，或独立／远端 MC 服务器）
  MCBOT 服务端组件 → Bot 身体

用户自己的 MC 客户端 → 同一个游戏世界
```

| 部署 | Agent 在哪 | 身体在哪 | 本机额外负担与前提 |
| --- | --- | --- | --- |
| 单机默认 | 用户电脑 | 当前单机已运行的内置服务器 | 控制桥＋Bot 增量逻辑；无第二个游戏实例，正常服务端模拟开销可接受 |
| 联机默认 | 用户电脑 | 服主安装组件的 MC 服务器 | 本机控制桥；服务端承担 Bot 模拟，需服主配置权限 |
| 可选 Agent 主机 | 用户明确选择的另一台机器 | 与上面相同 | Agent 认证／记忆在所选主机维护，不自动复制本机凭据 |

同机保持 loopback；异机优先评估受保护的隧道／鉴权通道，不能直接把现有 HTTP 控制口暴露公网。先证明身体可行，再落实跨设备传输；现有 loopback 原型不能称为已完成远程部署。MCBOT 的身体 token 与模型凭据分别管理。

## 3. 路线比较与建议

| 路线 | 对新约束的符合度 | 已知限制 | 本次建议 |
| --- | --- | --- | --- |
| Mineflayer／轻量协议身体 | 本机无第二套 MC；已有可玩证据 | 任意内容 Mod 的注册表、数据组件和自定义协议不能靠统一入口自动解决 | 保留给已验证的原版／插件／兼容环境 |
| ServerBody | 可以省去额外 Bot 客户端；Agent 可留本机 | 要安装服务端组件；独服生命周期和原版保护已验，更多内容Mod玩法／单机／异机仍待验 | **当前原型主线，按已验能力逐步扩展** |
| 本地完整 ClientBody | 已有部分实际功能证据 | 第二套整合包的内存／CPU／渲染负担，不符合默认低资源前提 | 撤销默认主线地位，保留已有实现，不继续扩大 |
| 无渲染客户端 | 可能降低图形负担 | 仍运行客户端／Mod；具体内存和 Mod 兼容性未测，不能保证大型包低开销 | 不作为默认问题已经解决的依据 |
| 异机 ClientBody | 可移走本机游戏负担 | 需要另一台运行整合包的设备；成本转移，不是消失 | 后续可选，不强制 Agent 随之迁移 |

[HeadlessMC 官方说明](https://github.com/headlesshq/headlessmc)确认其无窗口模式仍启动 Minecraft 客户端。由此只能判断它是另一种客户端运行方式，不能从“无窗口”推出“不占整合包内存”。

ServerBody 的可适配范围重点是服务器已经具备的注册表、碰撞、物品和交互。纯客户端按键、专用 GUI、客户端自定义消息流程，以及主动拒绝假玩家的 Mod，仍可能需要适配器或明确不支持。安装服务端组件也不能推出全部 Mod 功能自动兼容。

## 4. 旧计划中需要纠正的技术假设

| 旧假设／易产生的误解 | 源码核对与实际影响 |
| --- | --- |
| NeoForge 自带 FakePlayer 就是完整 Bot | `FakePlayer.tick()` 为空、默认无敌，`openMenu()` 返回空；它是用于模拟玩家交互的基础，不是现成陪玩角色 |
| 生成一个 ServerPlayer 就会被所有玩家看到 | 客户端需要先收到 PlayerInfo，再收到实体；需验证玩家列表注册、当前观察者、后加入者、离开追踪范围后返回 |
| 给假连接补一个 tick 即可 | 正常世界 tick 与网络 `doTick()` 分担逻辑；网络监听器还会重置位置。错误组合可能双 tick、不移动或回滚 |
| 直接调服务端交互等于普通玩家权限 | 一些距离、出生保护与世界交互检查位于网络包处理层，内部 `useItemOn()` 不能替代完整检查；Mod 事件也必须生效 |
| 多一个实体几乎不耗资源 | ServerPlayer 会加入玩家区块追踪与模拟范围；远离真人可能加载／生成新区域，连带运行机器、实体和其他 Mod。此事实保留，但用户接受正常服务端开销，不据此设置性能预算关口 |
| 单机与独服完全一样 | IntegratedServer 暂停时不执行常规世界 tick；心跳、超时、租约及恢复第一步需要单独定义 |
| ServerBody 可以保留所有客户端视觉 | 服务端没有 Bot 的渲染视角；结构化观察可保留，第一人称图片能力需另做选择，不能默认承诺 |

依据：本地 MC 1.21.1／NeoForge 21.1.217 编译源码中的 `FakePlayer`、`PlayerList.placeNewPlayer`、`ClientPacketListener.createEntityFromPacket`、`ChunkMap.addEntity/updatePlayerStatus`、`ServerGamePacketListenerImpl.tick/handleUseItemOn`、`ServerPlayerGameMode`、`IntegratedServer.tickServer`。该段源码预查时尚未运行实验；随后已完成的 ServerBody 实测另见 [验证记录](archive/server_body_validation.md)。

[NeoForge 1.21.1 FakePlayer 源码](https://raw.githubusercontent.com/neoforged/NeoForge/1.21.1/src/main/java/net/neoforged/neoforge/common/util/FakePlayer.java)可复核基础限制。[Carpet 的 ServerPlayer 实现](https://github.com/gnembon/fabric-carpet/blob/master/src/main/java/carpet/patches/EntityPlayerMPFake.java)证明有可参考的实现模式，但它的当前版本／加载器不同，不能当成 NeoForge 原型已经可用；复用第三方代码还要核对许可证。

## 6. 可行性关口（已进入有限验证）

每个能力与部署关口给出独立证据，失败先修订假设，不把通过的场景外推到未验场景。关口编号不是要求所有平台全部串行完成：首次独服试玩只依赖该部署的控制、交互与 Agent 验收；单机、异机和内容 Mod 分别约束相应支持声明。具体 A–E 批次见 [交付清单](delivery_plan.md)。

当前 G0／G1 独服基础物理、A 的真实租约与宿主停止、B 的原版重生／生存交互／保护及 C 本机真实 Agent 均有实测。D已有普通未运转Iron Furnace有限样本；单机暂停、异机及更多Mod玩法仍待各自关口。最新交互增量见[有限采集记录](archive/server_gather_validation.md)。

| 关口 | 最小实验 | 通过标准／失败时的处理 |
| --- | --- | --- |
| G0：角色与生命周期 | 一个固定身份，无真实 Bot 客户端，明确接管后生成；覆盖当前观察者／后加入／重新追踪、移除和重启 | 可见、唯一、可清理；不能正常注册或存在重复实体则停止上层迁移 |
| G1a：独服物理与控制 | 基础物理已验；接下来通过正式控制链验证租约、停止、进程退出和迟到请求 | 不穿墙、不回滚、不重复 tick；旧控制不能恢复；命令入口实测不代替新通道验收 |
| G1b：单机生命周期 | 内置服务器暂停超过租约、恢复、失焦、退出重进 | 恢复第一步先废弃过期控制；通过前不声明单机可用，不阻塞原版独服首轮试玩 |
| G2a：生存交互与保护 | 原版单格挖放、消耗和掉落、标准容器、保护区／取消事件 | 使用正常规则，拒绝时世界与库存不被误改；RCON 仅夹具和独立核对，不替身体执行动作 |
| G2b：内容 Mod 样本 | B 批次后尽早验证一个内容 Mod，记录注册 ID、碰撞、交互和容器边界 | 通过前不声明 Mod 原型可玩；标准能力与特殊 GUI 分别报告，不外推为全部 Mod 兼容 |
| G3a：本机部署边界 | 核对 Agent、控制桥和游戏进程，以及凭据位置 | 无额外 Bot MC 实例；Agent／模型凭据留在 Agent 主机，游戏组件仅获游戏控制凭据 |
| G3b：可选异机 | 受保护的控制通道、独立的 Agent／游戏主机配置、断链停止 | 用户选择 Agent 环境，不自动迁移账号；不得把现有 loopback 原型当成远程已经支持；服务端成本不设预算 |
| G4：本机 Agent 闭环 | 本机 Claude Code 经本机 MCP 控制该身体；查询、聊天唤醒、动作、停止、Agent 重启 | 账号仍本机，MC 服务器没有模型凭据；重启不重放任务；随后再复验 Codex 与可选异机 Agent 部署 |

不再要求先确定服务端性能预算或完成资源对照实验。第一版单 Bot；仍需避免任务规划／寻路无上限占用游戏主线程、重复 tick 或观察隐式生成未知区块，这些属于实现正确性与稳定性问题，不把正常服务端成本重新作为选型障碍。

单机暂停必须独立验收：暂停超过租约期、失焦、保存卡顿、退出重进与电脑睡眠；恢复后先撤销过期控制再允许动作。不能仅增大超时来掩盖迟到指令。首个实验允许明确停止并重新接管，不先做复杂自动恢复。

## 7. 本次建议结论

- **必须改变**：不再把本地第二个完整客户端作为 V1 默认路径；取消此前“基础能力一律不要求服主安装组件”的绝对约束。
- **必须保留**：Agent 默认本机且可选异机；凭据与游戏服务器分离；多 Agent／原生 API；Body 独立；广泛适配和多版本目标；默认不再运行第二套 MC 客户端，避免不必要的 Agent 侧负载。
- **已明确接受**：服务端 Bot 的正常模拟开销，不再作为方案否决条件或独立性能预算关口。
- **继续推进的方向**：ServerBody 已有基本控制、生存交互及本机 Agent 实证，继续完善任务交互；不据此承诺全部 Mod 兼容。
- **下一批边界**：走近、D普通未运转Iron Furnace、持续陪伴及有限采集首批已验。按用户确认的顺序跟随拾取也已通过，继续持续陪挖，再做小型建筑预设；机器运行／熔炼后置，单机／远端分别验收。

此前独立客户端与25566测试服已关闭；25567内容Mod样本及25568普通隔离服均已保存关闭。最新跟随拾取只更新25568的验证jar和专用存档夹具，配置已按备份恢复实际字节；正式服与启动器未动。此前全部未提交改动保留，不提交／推送。后续会话继续使用中文、PowerShell 7；非必要禁止任何哈希／指纹计算或校验，比较实际字节或字段。
